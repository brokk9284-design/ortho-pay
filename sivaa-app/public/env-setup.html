Supabase — Project URL & API Keys

Docs: supabase.com/docs/api-keys

ORTHO-PAY uses Supabase for authentication, database, and Row Level Security. You need three values from a single Supabase project. If you don't have a project yet, create one first at supabase.com/dashboard.

Prerequisite — Create a Supabase Project (if you haven't):
  1. Go to supabase.com/dashboard and sign in.
  2. Click New Project inside any organization.
  3. Enter a project name (e.g. ORTHO-PAY), set a strong database password, and pick a region close to your users.
  4. Click Create project and wait ~2 minutes for provisioning to finish.
NEXT_PUBLIC_SUPABASE_URL Required

Your project's unique API URL. Used by both client and server to connect to Supabase.

  1. Go to the Supabase Dashboard: Settings → API Keys
  2. If you don't see the URL at the top, click the Connect button in the dashboard header.
  3. Look for the field labeled Project URL. It looks like https://<project_ref>.supabase.co
  4. Copy this URL — this is your NEXT_PUBLIC_SUPABASE_URL value.
NEXT_PUBLIC_SUPABASE_ANON_KEY Required

Public-safe key (JWT format) used by the client-side Supabase client. Access is guarded by RLS policies.

  1. In the same Settings → API Keys page, scroll to the keys section.
  2. Find the row labeled anon (or publishable on newer projects).
  3. Click the Copy button next to it. The key starts with eyJ... (JWT) or sb_publishable_... (new format).
  4. This is your NEXT_PUBLIC_SUPABASE_ANON_KEY value.
Note: Both the legacy anon key and the new sb_publishable_ key work. Either is safe to expose in client-side code — RLS policies protect your data.
SUPABASE_SERVICE_ROLE_KEY Required

Server-only secret key that bypasses Row Level Security. Used in API routes for admin operations. Never expose this in client-side code.

  1. Stay on the Settings → API Keys page.
  2. Find the row labeled service_role (or secret on newer projects).
  3. Click Reveal to show the full key, then click Copy. It starts with eyJ... (JWT) or sb_secret_... (new format).
  4. This is your SUPABASE_SERVICE_ROLE_KEY value.
Security Warning: The service role key bypasses all RLS policies. Only use it in server-side API routes. Never commit it to git or expose it in the browser. If compromised, rotate it immediately in the same dashboard page.

GitHub — Storage Repository & Access Token

Docs: docs.github.com → PAT

ORTHO-PAY uses a private GitHub repository as object storage for KYC documents and payment receipts. You need to create the repo and generate a Personal Access Token (PAT) with write access to it.

Prerequisite — Create the Storage Repository:
  1. Go to github.com/new
  2. Set Repository name to ORTHO-PAY-storage
  3. Set visibility to Private — this is critical. User documents must not be public.
  4. Check Add a README file to initialize the repo.
  5. Click Create repository.
GITHUB_STORAGE_TOKEN Required

A Personal Access Token with read/write access to the ORTHO-PAY-storage repository. Used by the server to upload, list, and delete files via the GitHub Contents API.

Option A — Fine-grained PAT (recommended by GitHub):

  1. Go to GitHub → Settings → Developer settings → Fine-grained personal access tokens → Generate new token
  2. Under Token name, enter ORTHO-PAY Storage
  3. Under Expiration, select 1 year (or longer if your org allows it).
  4. Under Resource owner, select your personal account (or the org that owns the repo).
  5. Under Repository access, select Only select repositories, then choose ORTHO-PAY-storage from the dropdown.
  6. Under Permissions → Repository permissions, find Contents and set it to Read and write.
  7. Click Generate token.
  8. Copy the token immediately — it starts with github_pat_ and will not be shown again.
  9. This is your GITHUB_STORAGE_TOKEN value.

Option B — Classic PAT (simpler, less granular):

  1. Go to GitHub → Settings → Developer settings → Personal access tokens (classic) → Generate new token
  2. Under Note, enter ORTHO-PAY Storage
  3. Under Expiration, select No expiration or a date at least 1 year out.
  4. Under Scopes, check repo (Full control of private repositories). This automatically checks all sub-scopes including repo:contents.
  5. Click Generate token.
  6. Copy the token immediately — it starts with ghp_ and will not be shown again.
  7. This is your GITHUB_STORAGE_TOKEN value.
Security Warning: This token grants write access to your storage repo. Only use it in server-side environment variables. Never commit it to git or expose it in client-side code. If compromised, revoke it immediately at github.com/settings/tokens.
GITHUB_STORAGE_OWNER Required

The GitHub username or organization name that owns the ORTHO-PAY-storage repository.

  1. Go to your repository on GitHub: github.com
  2. Navigate to the ORTHO-PAY-storage repository.
  3. Look at the URL in your browser: github.com/<owner>/ORTHO-PAY-storage
  4. The <owner> part is your GITHUB_STORAGE_OWNER value. For example, if the URL is github.com/Sav-Dev/ORTHO-PAY-storage, the value is Sav-Dev.
GITHUB_STORAGE_REPO Optional

The name of the storage repository. Defaults to ORTHO-PAY-storage if not set.

  1. If you named your repo ORTHO-PAY-storage as instructed above, you can omit this variable entirely — the app defaults to it.
  2. If you used a different name, set this to that exact name (case-sensitive).
GITHUB_STORAGE_BRANCH Optional

The branch to upload files to. Defaults to main if not set.

  1. If your repo's default branch is main (the GitHub default), you can omit this variable.
  2. If you renamed the default branch (e.g. to master or storage), set this to that branch name.

Resend — Transactional Email API

Docs: resend.com/docs

ORTHO-PAY uses Resend to send transactional emails: welcome emails on registration, 2FA codes for payment authorization, password reset links, payment confirmation receipts, payment request notifications, and escrow status updates (approved/rejected).

RESEND_API_KEY Required

API key for the Resend email API. Used server-side to send all transactional emails.

  1. Go to resend.com/api-keys and sign in (or create a free account at resend.com).
  2. Click Create API Key.
  3. Enter a name like ORTHO-PAY Production.
  4. Select the permission level — Sending access is sufficient (full access also works).
  5. Click Create.
  6. Copy the key immediately — it starts with re_ and will not be shown again.
  7. This is your RESEND_API_KEY value.
Testing mode: With a free Resend account, you can only send emails to your own verified email address (the one you signed up with). To send to any recipient, you must verify a custom domain on Resend.
RESEND_FROM_ADDRESS Optional

The sender email address that appears in the "From" field of all ORTHO-PAY emails. Defaults to ORTHO-PAY <onboarding@resend.dev> for testing.

  1. If you're using the free Resend tier (no custom domain), leave this unset — the app defaults to ORTHO-PAY <onboarding@resend.dev>.
  2. If you've verified a custom domain on Resend, set this to your branded address, e.g. ORTHO-PAY <noreply@ORTHO-PAY.com>.

Integration Guides

How to connect the three services together so ORTHO-PAY can authenticate users, store files, and send emails.

A. Link Supabase Auth with Resend (Custom SMTP)

By default, Supabase sends auth emails (password reset, email confirmation) from noreply@mail.app.supabase.io. To send these through Resend with your own domain, configure custom SMTP in Supabase.

Supabase Auth ──SMTP──▶ Resend SMTP ──sends──▶ User Inbox
  1. Log into your Supabase Dashboard.
  2. Go to Authentication in the left sidebar.
  3. Scroll to the SMTP Settings section under Notifications or Email.
  4. Toggle Enable Custom SMTP to ON.
  5. Enter the following Resend SMTP credentials:
    • Host: smtp.resend.com
    • Port: 465
    • Username: resend
    • Password: Your Resend API key (starts with re_)
    • Sender email: onboarding@resend.dev (or your custom domain email)
    • Sender name: ORTHO-PAY
  6. Click Save. All Supabase auth emails (password reset, email confirmation, magic links) will now be sent through Resend.
Alternative — Resend's native Supabase integration: You can also connect Supabase directly from Resend. Go to resend.com/integrations, click Connect to Supabase, select your project, and Resend will auto-configure the SMTP settings for you.

B. Link Vercel with Resend (Environment Variables)

When deploying ORTHO-PAY to Vercel, you need to add the Resend API key as an environment variable so the Next.js API routes can send emails.

Vercel Project ──env: RESEND_API_KEY──▶ Next.js API Route ──calls──▶ Resend API ──sends──▶ User Inbox
  1. Go to your Vercel Dashboard and open your ORTHO-PAY project.
  2. Go to Settings → Environment Variables.
  3. Add the following variables:
    • RESEND_API_KEY = your Resend API key (re_...)
    • RESEND_FROM_ADDRESS = ORTHO-PAY <onboarding@resend.dev> (or your custom domain)
    • NEXT_PUBLIC_SUPABASE_URL = your Supabase project URL
    • NEXT_PUBLIC_SUPABASE_ANON_KEY = your Supabase anon key
    • SUPABASE_SERVICE_ROLE_KEY = your Supabase service role key
    • GITHUB_STORAGE_TOKEN = your GitHub PAT
    • GITHUB_STORAGE_OWNER = your GitHub username
  4. Click Save for each variable.
  5. Redeploy your project for the variables to take effect.
Alternative — Vercel Marketplace: You can install Resend directly from the Vercel Marketplace. This auto-creates a Resend API key and adds it as RESEND_API_KEY to your Vercel project's environment variables in one step. Run: vc i resend -m domain=yourdomain.com

C. Link Supabase with Vercel (Database Connection)

Vercel needs to connect to your Supabase PostgreSQL database. The connection string is already in your NEXT_PUBLIC_SUPABASE_URL (HTTP API URL), but for direct database access (e.g., from Vercel functions), use the connection string.

Vercel Function ──@supabase/ssr──▶ Supabase API ──queries──▶ PostgreSQL
  1. In your Supabase Dashboard, go to Project Settings → Database.
  2. Find the Connection String section and copy the URI (pooler connection, port 6543).
  3. In your Vercel project, go to Settings → Environment Variables.
  4. Add NEXT_PUBLIC_SUPABASE_URL with the HTTP API URL (https://<ref>.supabase.co).
  5. Add NEXT_PUBLIC_SUPABASE_ANON_KEY and SUPABASE_SERVICE_ROLE_KEY from Settings → API Keys.
  6. Redeploy for the variables to take effect.
Important: The NEXT_PUBLIC_SUPABASE_URL must be the HTTP API URL (https://<ref>.supabase.co), NOT the PostgreSQL connection string. The @supabase/ssr client uses the HTTP API, not direct database connections.

Your .env.local file should look like this:

# ─── Supabase (from Settings → API Keys) ───
NEXT_PUBLIC_SUPABASE_URL=https://yourprojectref.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
SUPABASE_SERVICE_ROLE_KEY=eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...

# ─── GitHub Storage (from Settings → Developer settings → Tokens) ───
GITHUB_STORAGE_TOKEN=github_pat_xxxxxxxxxxxxxxxxxxxxxxxxxxxx
GITHUB_STORAGE_OWNER=your-github-username
GITHUB_STORAGE_REPO=ORTHO-PAY-storage
GITHUB_STORAGE_BRANCH=main

# ─── Resend (from resend.com/api-keys) ───
RESEND_API_KEY=re_xxxxxxxxxxxxxxxxxxxxxxxxxxxx
RESEND_FROM_ADDRESS=ORTHO-PAY <onboarding@resend.dev>
