1. Executive Overview — The P2P Model

ORTHO-PAY is being restructured from a traditional payment platform to a peer-to-peer (P2P) escrow matching platform. In the traditional model, the platform holds funds and processes deposits/withdrawals directly. In the P2P model, users fund and defund their ORTHO-PAY wallets by exchanging value with other users, not with the platform itself.

The key insight:

  • Depositing = A user with external money (e.g., Cash App balance) sends it to a peer who wants to exit ORTHO-PAY. In return, the depositor receives ORTHO-PAY wallet balance from the peer.
  • Withdrawing = A user with ORTHO-PAY balance sends it to a peer who wants to deposit. In return, the withdrawer receives external money (e.g., Cash App, Bitcoin) from the peer.
  • Sending = User-to-user transfer within ORTHO-PAY, held in escrow and admin-reviewed before release.

The platform never holds external funds directly. Instead, it facilitates matching between users with complementary needs and holds ORTHO-PAY balance in escrow during the matching process.

2. Core Concept: How P2P Matching Works

The Liquidity Matching Principle

Think of ORTHO-PAY as a liquidity matching engine. Every deposit creates a "need" and every withdrawal creates a "supply" — or vice versa. The platform matches them.

USER A (Depositor) USER B (Withdrawer) ┌─────────────────────┐ ┌─────────────────────┐ │ Has: Cash App $100 │ │ Has: ORTHO-PAY $100 │ │ Wants: ORTHO-PAY $ │ │ Wants: Cash App $ │ └─────────┬───────────┘ └───────────┬─────────┘ │ │ │ ┌─────────────────┐ │ └────────►│ P2P MATCHING │◄──────────┘ │ ENGINE │ │ (Escrow Hold) │ └────────┬────────┘ │ ┌──────────┴──────────┐ │ │ ▼ ▼ USER A receives USER B receives ORTHO-PAY $100 Cash App $100 (wallet credited) (external payment) PLATFORM: Facilitates match, holds escrow, takes fee

What happens step by step:

  1. User A wants to deposit $100 via Cash App → they have $100 in Cash App and want ORTHO-PAY balance.
  2. User B wants to withdraw $100 to Cash App → they have $100 in ORTHO-PAY and want Cash App balance.
  3. The platform matches A and B based on: amount, payment method, and availability.
  4. User B's $100 ORTHO-PAY balance is locked in escrow.
  5. User A sends $100 via Cash App to User B's Cash App handle (provided by the platform).
  6. User A confirms payment → admin reviews → approves.
  7. On approval: User A's ORTHO-PAY wallet is credited $100 (from escrow, previously User B's balance). User B has already received $100 externally via Cash App.
  8. Platform charges a fee (e.g., 2% = $2) — deducted from the transfer.

3. System Actors & Roles

Actor Description Key Actions
User (Depositor) A user who has external funds (Cash App, Venmo, BTC, etc.) and wants to add ORTHO-PAY wallet balance. Selects payment method, enters amount, sends external payment to matched peer, confirms payment
User (Withdrawer/Peer) A user who has ORTHO-PAY balance and wants to convert it to external funds (Cash App, Venmo, BTC, etc.). Creates withdrawal request, provides external payment details, receives external payment from depositor
User (Sender) A user sending ORTHO-PAY balance to another ORTHO-PAY user via $paytag. Enters recipient $tag + amount, funds locked in escrow, awaits admin approval
User (Receiver) A user receiving ORTHO-PAY balance from another user. Receives funds to wallet after escrow approval
Admin Platform staff who review and approve/reject transactions. Reviews escrow transactions, approves/rejects, manages users, manages payment methods, manages fees
Escrow System The automated system that locks funds during transactions. Locks sender balance, releases to receiver on approval, refunds on rejection
Matching Engine The automated system that matches depositors with withdrawers (new in P2P model). Matches based on amount, payment method, limits, KYC status; creates match orders

4. Current Architecture vs Proposed P2P Architecture

Current Model (Centralized)

  • User deposits → sends money to platform's Cash App/PayPal/BTC address
  • Admin manually verifies receipt → credits wallet
  • User withdraws → admin sends money from platform's accounts to user
  • Platform must maintain balances across all payment methods
  • Platform is the counterparty in every deposit/withdrawal
  • Scaling requires more platform liquidity
  • Risk: platform holds user funds externally

Proposed P2P Model

  • User deposits → matched with a peer who wants to withdraw
  • Depositor sends external payment directly to peer's Cash App/PayPal/BTC
  • Peer's ORTHO-PAY balance transfers to depositor (via escrow)
  • Platform never holds external funds
  • Users are the counterparties — platform is matchmaker + escrow agent
  • Scaling = more users = more liquidity (network effect)
  • Risk: peer doesn't send external payment (mitigated by escrow + admin review)

Why P2P is Better for ORTHO-PAY

The P2P model eliminates the need for ORTHO-PAY to maintain external balances across Cash App, Venmo, PayPal, Bitcoin, etc. The platform becomes a pure matchmaker and escrow agent. Revenue comes from matching fees, not from float or spread. This is more capital-efficient and scales with user growth.

5. Workflow: Deposit (P2P Inflow)

A "deposit" in the P2P model means: "I have external money and want ORTHO-PAY balance."

Deposit Flow — Step by Step
1

User Creates Deposit Request

Depositor selects payment method (e.g., Cash App) and enters amount (e.g., $100). The system creates a deposit_order with status pending_match.

2

Matching Engine Finds a Peer

Matching Engine searches for a withdrawal_order with: same payment method, same or higher amount, status pending_match. If found, creates a p2p_match linking the two orders. Both orders move to matched status.

If no match found: deposit order stays in pending_match and is queued. User can cancel.

3

Escrow Lock

Escrow System locks the withdrawer's ORTHO-PAY balance (e.g., $100 from User B's wallet). This ensures the peer can't spend or withdraw it elsewhere. Both users see the match details and each other's payment handle (Cash App $tag, PayPal email, BTC address, etc.).

4

Depositor Sends External Payment

Depositor sends $100 via Cash App to the withdrawer's Cash App $tag (shown in the app). The depositor then clicks "I have made payment" and optionally uploads a receipt/screenshot.

5

Withdrawer Confirms Receipt

Withdrawer checks their Cash App, confirms they received the $100. Clicks "Payment received." If the withdrawer disputes (says they didn't receive), it goes to admin review.

6

Admin Review & Approval

Admin reviews the match: verifies the depositor's payment screenshot, checks the withdrawer's confirmation, and approves or rejects.

If approved: escrow releases $100 (minus fee) to depositor's wallet. Withdrawer already has the external $100.

If rejected: escrow refunds $100 to withdrawer's wallet. Depositor must resolve externally.

7

Completion

Depositor's wallet is credited. Withdrawer's wallet is debited (already locked). Fee is split or charged to one party. Both parties notified. Transaction chat is available for dispute resolution.

Key Risk: Depositor Doesn't Send External Payment

If the depositor claims they sent payment but didn't, the withdrawer disputes. Admin reviews evidence (receipt screenshot, Cash App transaction ID). If no payment was sent, escrow refunds the withdrawer. The depositor may be flagged/banned.

Key Risk: Withdrawer Claims Not Received (But Actually Received)

If the withdrawer lies about not receiving the external payment, admin reviews the depositor's receipt. If evidence shows payment was sent, admin can force-approve. The withdrawer may be flagged/banned.

6. Workflow: Withdrawal (P2P Outflow)

A "withdrawal" in the P2P model means: "I have ORTHO-PAY balance and want external money."

Withdrawal Flow — Step by Step
1

User Creates Withdrawal Request

Withdrawer selects desired payment method (e.g., "I want to receive via Cash App") and enters amount (e.g., $100). Provides their Cash App $tag for receiving. System creates a withdrawal_order with status pending_match.

KYC must be verified. 2FA code required. Available balance is checked.

2

Matching Engine Finds a Depositor

Matching Engine searches for a deposit_order with: same payment method, same or lower amount, status pending_match. If found, creates a p2p_match. Both orders move to matched status.

If no match found: withdrawal order stays queued. User can cancel (funds remain in wallet, not locked until matched).

3

Escrow Lock

Escrow System locks the withdrawer's ORTHO-PAY balance ($100 + fee). The withdrawer's available balance decreases. Both users can now see the match and each other's payment details.

4

Depositor Sends External Payment to Withdrawer

Depositor sends $100 via Cash App to the withdrawer's $tag. Clicks "I have made payment" and uploads receipt.

5

Withdrawer Confirms Receipt

Withdrawer verifies $100 received in their Cash App. Clicks "Payment received."

6

Admin Review & Approval

Admin reviews evidence and approves. Escrow releases: withdrawer's locked balance is debited (sent to depositor's wallet). Withdrawer has already received external funds.

7

Completion

Withdrawer's wallet debited. Depositor's wallet credited. Fee deducted. Both notified. Chat available for disputes.

Important: Partial Matches

A $500 withdrawal can be matched with multiple smaller deposits (e.g., $200 + $300). The matching engine should support partial matching to improve liquidity. Each partial match is a separate escrow transaction.

7. Workflow: Send Money (P2P Transfer)

Sending money is a direct user-to-user transfer within ORTHO-PAY. This is the core escrow-protected payment flow.

Send Money Flow — Step by Step
1

Sender Initiates Payment

Sender enters recipient's $ORTHO tag (e.g., $alice) and amount (e.g., $50). System verifies recipient exists, both wallets are active, sender has sufficient balance, both users are KYC verified.

2

Fee Calculation & Escrow Lock

System calculates fee based on fee rules (e.g., 3% for <$50, 2% for $50–$499, 1% for $500+). Sender's gross amount ($50) is locked in escrow. Sender's available balance decreases. Payment status: escrow_held.

3

Admin Review

Admin reviews the transaction for fraud, suspicious patterns, or policy violations. Admin can approve or reject.

4

Approval → Release

If approved: $50 gross is debited from sender (total_sent increases), $48.50 net (after $1.50 fee) is credited to receiver (total_received increases). Escrow lock released. Payment status: completed.

Both parties notified via in-app notification + email. Transaction chat created/updated with system message.

5

Rejection → Refund

If rejected: $50 is refunded to sender (locked_balance decreases). Payment status: reversed. Sender notified. No fee charged.

8. Workflow: Request Money

A user can request money from another ORTHO-PAY user. This is a notification + optional payment method selection.

Request Money Flow — Step by Step
1

Requester Creates Payment Request

Requester enters recipient's $tag, amount, and optional message. System verifies both users exist, are KYC verified, and have active wallets. Prevents duplicate pending requests between same pair.

2

Recipient Notified

System sends in-app notification + email to the recipient. A transaction chat is auto-created with a system message about the request.

3

Recipient Reviews & Pays

Recipient sees the request in their dashboard. They can accept (triggers the Send Money flow — step 1 of Send) or decline.

4

Payment Processed

If recipient accepts: the standard Send Money flow executes (escrow lock → admin review → release). Request status updates to paid.

If recipient declines: request status → declined. Requester notified.

5

Expiration

If no action within 7 days, request auto-expires. Status → expired. Requester can create a new one.

9. P2P Matching Engine — Algorithm & Logic

Matching Algorithm (Proposed)

Inputs:

  • Deposit orders (pending_match): { user_id, amount, payment_method, created_at }
  • Withdrawal orders (pending_match): { user_id, amount, payment_method, external_details, created_at }

Matching Rules (Priority Order):

  1. Exact match — Same payment method + same amount. Highest priority. Instant match.
  2. Partial match (withdrawer ≥ depositor) — Same payment method, withdrawer's amount ≥ depositor's amount. The withdrawal is partially fulfilled. Remaining withdrawal amount stays in queue.
  3. Partial match (depositor ≥ withdrawer) — Same payment method, depositor's amount ≥ withdrawer's amount. The deposit is partially fulfilled. Remaining deposit amount stays in queue.
  4. FIFO tiebreaker — If multiple candidates, match with the oldest order first (fairness).

Constraints:

  • Both users must be KYC verified
  • Both wallets must be active
  • Users cannot be matched with themselves
  • Payment method must match exactly (Cash App ↔ Cash App, BTC ↔ BTC, etc.)
  • Amount must be within payment method min/max limits
  • Withdrawer's available balance must cover the amount + fee

Matching Modes:

Auto-Match (Default)

System automatically matches orders as they come in. Fastest liquidity. Admin still reviews each match before escrow release.

Manual Match (Optional)

User sees a list of available counterparties and picks one. More control, slower. Could be a premium feature.

Pseudocode:

function findMatch(depositOrder):
  candidates = SELECT * FROM withdrawal_orders
    WHERE status = 'pending_match'
    AND payment_method = depositOrder.payment_method
    AND user_id != depositOrder.user_id
    AND kyc_status = 'verified'
    AND wallet_status = 'active'
    ORDER BY created_at ASC

  // 1. Try exact match
  for candidate in candidates:
    if candidate.amount == depositOrder.amount:
      return createMatch(depositOrder, candidate, candidate.amount)

  // 2. Try partial match (withdrawer has more)
  for candidate in candidates:
    if candidate.amount >= depositOrder.amount:
      return createMatch(depositOrder, candidate, depositOrder.amount)
      // candidate.remaining = candidate.amount - depositOrder.amount

  // 3. Try partial match (depositor has more)
  for candidate in candidates:
    if candidate.amount <= depositOrder.amount:
      return createMatch(depositOrder, candidate, candidate.amount)
      // depositOrder.remaining = depositOrder.amount - candidate.amount

  return null // No match found, queue the order

10. Escrow & Admin Review Process

Escrow Lifecycle
Stage Status Funds State Who Acts Next
Order created pending_match Not locked Matching engine
Matched matched Withdrawer's balance locked Depositor (send external payment)
Payment sent payment_sent Still locked Withdrawer (confirm receipt)
Receipt confirmed under_review Still locked Admin (review & approve)
Approved completed Released to depositor — (done)
Rejected reversed Refunded to withdrawer — (done)
Disputed disputed Still locked Admin (investigate)
Cancelled (pre-match) cancelled Never locked — (done)

Admin Review Checklist:

  • Verify depositor's payment screenshot/receipt is legitimate
  • Check withdrawer confirmed receipt
  • Check for suspicious patterns (new account, large amount, repeated disputes)
  • Verify both users' KYC status
  • Check transaction chat for any dispute messages
  • Approve or reject with optional notes

Proposed P2P Fee Model:

  • Send Money (user-to-user): Fee charged to sender (deducted from gross amount). Receiver gets net. Same as current.
  • Deposit (P2P match): Fee charged to depositor (e.g., 1-2%). The depositor pays $100 externally but receives $98-$99 in ORTHO-PAY wallet. The difference is the platform fee.
  • Withdrawal (P2P match): Fee charged to withdrawer (e.g., 1-2%). The withdrawer gives up $100 ORTHO-PAY but receives $98-$99 externally. The difference is the platform fee.
  • Subscription tiers (existing): Personal ($0/mo, 3%), Business ($29/mo, 2%), Enterprise ($199/mo, 1%). These reduce the per-transaction fee.

Revenue Sources

1. Per-transaction fees (send, deposit match, withdrawal match) · 2. Subscription plans (Business, Enterprise) · 3. Premium features (priority matching, instant match)

12. KYC & Compliance

Current KYC Flow:

  1. User uploads ID document (passport, driver's license, state ID) in Settings → KYC
  2. Document stored in GitHub-based storage, record in kyc_documents table
  3. Profile kyc_status set to pending
  4. Admin reviews document in Admin Dashboard → KYC tab
  5. Admin approves → kyc_status = verified
  6. Admin rejects → kyc_status = rejected (user can re-upload)

KYC Requirements (P2P Model):

  • Must be verified before: sending money, requesting money, creating deposit/withdrawal orders
  • Both parties in a P2P match must be KYC verified — this is critical for AML compliance
  • Admin can freeze wallet if suspicious activity detected (wallet status → frozen/suspended)
  • GDPR/NDPR compliant data handling (legal pages already created at /terms, /privacy, /cookies)

13. Edge Cases & Conflict Resolution

Edge Case Handling

1. Depositor claims payment sent but withdrawer says not received

  • Admin reviews depositor's receipt/screenshot
  • Admin requests transaction ID from both parties
  • If evidence supports depositor: admin force-approves, withdrawer's locked balance is debited
  • If evidence supports withdrawer: admin rejects, depositor's order cancelled, withdrawer refunded
  • Repeat offenders are banned

2. Partial match — withdrawal $500 matched with deposit $200

  • $200 escrow transaction created and processed
  • Remaining $300 withdrawal stays in pending_match queue
  • Withdrawer sees two transactions: one completed ($200), one pending ($300)

3. User cancels deposit/withdrawal after match but before payment

  • If depositor cancels: match cancelled, withdrawer's balance unlocked, withdrawal re-queued
  • If withdrawer cancels: match cancelled, depositor's order re-queued
  • Cancellation penalty: possible fee or cooldown period for repeat cancellers

4. External payment fails (e.g., Cash App payment bounced)

  • Depositor reports failed payment → match status → disputed
  • Admin reviews, cancels match, both orders re-queued
  • No fee charged

5. User tries to match with themselves

  • System prevents: user_id != depositOrder.user_id in matching query

6. Wallet frozen during escrow

  • If withdrawer's wallet is frozen by admin during escrow: match is cancelled, depositor's order re-queued
  • If depositor's wallet is frozen: match cancelled, withdrawer's balance unlocked, withdrawal re-queued

7. No matching counterparty available

  • Order stays in pending_match queue
  • User sees "Searching for match..." status
  • User can cancel at any time (no penalty for first 3 cancellations per month)
  • System can notify user when a match becomes available

8. Rate limits and anti-fraud

  • Max 5 pending deposit/withdrawal orders per user
  • Max $10,000 daily deposit/withdrawal per user (configurable by admin)
  • New accounts (<7 days) limited to $500 per transaction
  • Admin can override limits per user

14. Proposed Database Schema Changes

New Tables for P2P Matching

Table: deposit_orders

CREATE TABLE deposit_orders (
  order_id        UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id         UUID REFERENCES profiles(id),
  payment_method_id UUID REFERENCES payment_methods(method_id),
  amount          DECIMAL(12,2) NOT NULL,
  matched_amount  DECIMAL(12,2) DEFAULT 0,      -- how much has been matched so far
  status          TEXT DEFAULT 'pending_match',  -- pending_match, matched, payment_sent, under_review, completed, cancelled, disputed
  created_at      TIMESTAMPTZ DEFAULT now(),
  updated_at      TIMESTAMPTZ DEFAULT now(),
  expires_at      TIMESTAMPTZ DEFAULT now() + INTERVAL '24 hours'
);

Table: withdrawal_orders

CREATE TABLE withdrawal_orders (
  order_id        UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id         UUID REFERENCES profiles(id),
  payment_method_id UUID REFERENCES payment_methods(method_id),
  amount          DECIMAL(12,2) NOT NULL,
  matched_amount  DECIMAL(12,2) DEFAULT 0,
  external_details JSONB NOT NULL,              -- { cashtag: "$alice", btc_address: "...", etc. }
  status          TEXT DEFAULT 'pending_match',
  two_fa_verified BOOLEAN DEFAULT false,
  created_at      TIMESTAMPTZ DEFAULT now(),
  updated_at      TIMESTAMPTZ DEFAULT now(),
  expires_at      TIMESTAMPTZ DEFAULT now() + INTERVAL '24 hours'
);

Table: p2p_matches

CREATE TABLE p2p_matches (
  match_id        UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  deposit_order_id  UUID REFERENCES deposit_orders(order_id),
  withdrawal_order_id UUID REFERENCES withdrawal_orders(order_id),
  depositor_id    UUID REFERENCES profiles(id),
  withdrawer_id   UUID REFERENCES profiles(id),
  payment_method_id UUID REFERENCES payment_methods(method_id),
  amount          DECIMAL(12,2) NOT NULL,       -- the matched amount
  fee_amount      DECIMAL(12,2) DEFAULT 0,
  status          TEXT DEFAULT 'matched',       -- matched, payment_sent, under_review, completed, reversed, disputed, cancelled
  depositor_confirmed BOOLEAN DEFAULT false,    -- depositor clicked "I have made payment"
  withdrawer_confirmed BOOLEAN DEFAULT false,   -- withdrawer clicked "Payment received"
  receipt_url     TEXT,                          -- depositor's payment screenshot
  escrow_wallet_tx_id UUID,                      -- reference to wallet_transactions for escrow hold
  admin_id        UUID,                           -- who approved/rejected
  admin_notes     TEXT,
  created_at      TIMESTAMPTZ DEFAULT now(),
  approved_at     TIMESTAMPTZ,
  expires_at      TIMESTAMPTZ DEFAULT now() + INTERVAL '2 hours'  -- time limit for payment
);

Existing Tables — Modifications:

  • deposits table: add order_id FK to deposit_orders, add match_id FK to p2p_matches. Keep existing columns for backward compatibility.
  • withdrawals table: add order_id FK to withdrawal_orders, add match_id FK to p2p_matches. Keep existing columns.
  • wallet_transactions: add new type p2p_match_hold and p2p_match_release.
  • payment_methods: add supports_p2p boolean column (some methods may be platform-only, not P2P).

Authentication & Authorization

Auth Flow:

  1. User registers with email + password + $ORTHO tag → profile created in Supabase Auth + profiles table
  2. OTP verification via email (6-digit code)
  3. Wallet auto-created on first login (status: active, balance: 0)
  4. Session managed via Supabase cookies (JWT-based)
  5. Middleware checks every request to /dashboard/* and /admin/*

Authorization Levels:

LevelFunctionWhoAccess
Public—AnyoneLanding, login, register, legal pages
AuthenticatedrequireAuth()Logged-in userDashboard, send, request, deposit, withdraw, chat, settings
AdminrequireAdmin()User with active admin recordAdmin dashboard: approve/reject payments, deposits, withdrawals, KYC, manage payment methods
Super AdminrequireSuperAdmin()Admin with role='super_admin'All admin powers + manage other admins

2FA (Two-Factor Authentication):

  • Required for: sending payments, fulfilling payment requests, withdrawals
  • Flow: user requests 2FA code → 6-digit code generated, hashed (SHA-256), stored in payment_2fa_codes table → emailed to user → user enters code → verified against hash → marked used
  • Code expires after 10 minutes
  • Only one unused code per purpose at a time (previous unused codes are invalidated)

Wallet & Balance System

Balance Formula:

available_balance = wallets.total_received - wallets.total_sent - wallets.locked_balance

Wallet Fields:

  • total_received — cumulative amount received (deposits approved, payments received)
  • total_sent — cumulative amount sent (withdrawals approved, payments sent)
  • locked_balance — funds held in escrow (pending payments, pending withdrawals)
  • status — active, frozen, suspended (admin can freeze)
  • currency — USD (single currency)

Transaction Types (wallet_transactions):

Escrow System — How It Works Today

Current Flow (Centralized):

  1. Sender initiates payment → system calculates fee (gross, fee, net amounts)
  2. Escrow lock → sender's locked_balance increased by gross amount. Payment status: escrow_held
  3. Admin reviews → checks for fraud, verifies both parties
  4. Admin approves → sender's total_sent += gross, locked_balance -= gross. Receiver's total_received += net. Payment status: completed
  5. Admin rejects → sender's locked_balance -= gross (refunded). Payment status: reversed
  6. Escrow review logged → escrow_reviews table records admin action + notes
  7. Both parties notified → in-app notification + email
  8. Transaction chat updated → system message posted with escrow status

What Changes in P2P Model:

The escrow mechanism stays the same for send money. For deposits and withdrawals, the escrow now locks the withdrawer's ORTHO-PAY balance (instead of the platform crediting from its own funds). The matching engine creates the link, and admin review confirms the external payment happened before releasing escrow.

Notification System

Every significant action generates notifications:

  • Payment sent → receiver notified "You received $X from $tag"
  • Escrow approved → both parties notified with amounts
  • Escrow rejected → sender notified "Payment refunded"
  • Deposit approved/rejected → user notified
  • Withdrawal approved/rejected → user notified
  • Payment request received → target user notified + emailed
  • KYC approved/rejected → user notified
  • New chat message → other party notified

Notifications have types: payment, escrow, deposit, withdrawal, general. Each notification has a read boolean for unread tracking.

Transaction Chat System

Every payment or payment request auto-creates a 1:1 chat between the two users:

  • transaction_chats — one chat per unique user pair (user_a_id is always the lower UUID for deduplication)
  • transaction_messages — messages with types: user (text), system (auto-generated events)
  • System messages include event types: request_created, escrow_approved, escrow_rejected
  • Read receipts: read_by_a and read_by_b booleans per message
  • File attachments supported: file_url, file_name, file_size
  • Messages limited to 2000 characters
Audit Logging

Every admin action is logged in audit_logs:

  • Actor: admin_id, actor_type (user/admin/system)
  • Action: "Approve deposit", "Reject withdrawal", "Create payment method", "Update payment method", "Delete payment method", "Approve KYC", "Reject KYC", "Approve payment", "Reject payment"
  • Target: table_name, record_id
  • Before/After: old_value, new_value (JSON)
  • Timestamp: when action occurred

CREATE OR REPLACE FUNCTION public.is_admin()
RETURNS BOOLEAN AS $$
  SELECT EXISTS (
    SELECT 1 FROM public.admins
    WHERE profile_id = auth.uid()
    AND is_active = true

18. Open Questions for Consultant

  1. Fee on P2P matches: Should the fee be charged to the depositor, the withdrawer, or split between both? Currently proposed: depositor pays on deposit match, withdrawer pays on withdrawal match. Is this fair?
  2. Partial matching: Should we support partial matches (e.g., $500 withdrawal matched with $200 + $300 deposits)? This improves liquidity but adds complexity. Recommended: yes, but phase 2.
  3. Auto-match vs manual match: Should auto-match be the default? Or should users see a list of available counterparties and choose? Auto-match is simpler and faster.
  4. Time limits: How long should a depositor have to send the external payment after a match? Currently proposed: 2 hours. Too short? Too long?
  5. Receipt requirement: Should uploading a payment receipt/screenshot be mandatory or optional? Mandatory reduces disputes but may frustrate users.
  6. Dispute resolution: Should there be a formal dispute process with evidence submission, or should admin just review and decide? Currently: admin reviews evidence and decides.
  7. Rating system: Should we add a user rating system (like Uber/Lyft) after each P2P match? This builds trust and helps identify bad actors.
  8. Liquidity provider role: Should there be "liquidity providers" — users who maintain large ORTHO-PAY balances specifically to match with depositors? They could earn a small premium. This is similar to market makers in trading.
  9. Regulatory concerns: Does the P2P model change our regulatory obligations? We're not holding external funds, but we're facilitating transfers. Does this make us a money transmitter? MSB registration needed?
  10. Crypto matching: For crypto deposits/withdrawals, the "external payment" is on-chain. Should we verify on-chain transactions automatically (via blockchain API) instead of relying on screenshots?
  11. Migration plan: Should we migrate existing deposits/withdrawals to the new P2P model, or run both in parallel? Recommended: new orders use P2P, existing pending orders processed under old model.
  12. Payment method details privacy: When users are matched, they see each other's Cash App $tag, PayPal email, or BTC address. Is this acceptable? Should we use a proxy/intermediary address instead?
Summary

The P2P restructure transforms ORTHO-PAY from a centralized payment processor to a decentralized liquidity matching platform with escrow protection. The platform's role shifts from holding funds to matching users and ensuring safe transactions through escrow + admin review.

Key Benefits:

  • No need to maintain external balances across payment platforms
  • Scales with user growth (network effect — more users = more liquidity)
  • Lower operational risk (platform doesn't hold external funds)
  • Revenue from matching fees + subscriptions
  • Users get more payment options (any method another user supports)

Key Risks:

  • Disputes between matched users (mitigated by escrow + admin review + receipt upload)
  • Liquidity shortage (not enough counterparties) — mitigated by partial matching + liquidity providers
  • Regulatory uncertainty (need legal opinion on P2P model)
  • Bad actors (mitigated by KYC, ratings, admin review, wallet freezing)
